SEAM 简介

Self-Evolving Agentic Migration for Chinese GPUs

适用用户

要用国产 GPU 的开发者、想了解国产 GPU 的开发者。

SEAM 解决的问题

在使用国产 GPU 前，用户担心可能会遇到问题：

  • 不好用：可能运行不起来或者精度差，适配耗时很久，购买国产 GPU 时间上不划算。
  • 缺参考：「别人真的跑通了吗？」「我这个模型有些偏冷门，能不能跑？」
  • 缺指导：国产 GPU 要怎么用？都说报错后搞半天找不到原因，搜不到别人经验参考。

使用国产 GPU 过程中，可能出现 3 类耗时问题：

  • 运行不起来：不同 GPU 平台的软件栈、驱动、算子库和 Python 依赖不同。一个项目即使在 NVIDIA GPU 上可以正常运行，换到国产 GPU 后也可能因为接口不兼容、依赖版本不匹配、自定义算子缺失等原因失败。迁移技术栈深、碎片化知识难掌握。
  • 缺少参考案例：用户往往不知道某个模型是否真的在目标国产 GPU 上跑通过，也不清楚失败是自己环境配置问题、代码问题，还是硬件平台适配问题。缺少可复现案例会影响用户对国产 GPU 的使用信心。
  • 迁移结果难以验证：代码改完并不等于迁移成功。项目可能只是启动了，但精度不对、性能异常，或者实际运行时回退到了 CPU。SEAM 强调通过真实运行和机器验证来确认迁移结果，而不是只依赖静态代码修改。
🐧 别担心，SEAM 会陪伴你用好中国国产 GPU。

SEAM 能力和技术方案简介

1. 多硬件 × 多框架覆盖

华为昇腾 NPU、阿里平头哥 PPU、沐曦 MetaX GPU 三家平台 × PyTorch / vLLM / SGLang 三类主框架均已完成适配；其他框架「等你提需求」。

2. 自动化端到端迁移

SEAM 当前实现的核心是一个由 YAML 状态机驱动的多阶段迁移流水线， 配合 5 个持久化智能体协同工作，基于当前 GPU 真实运行反馈。 整个流水线包含 8 个阶段：

GPU环境检测 → 用户项目分析 → 依赖准备 → 规则迁移 → 验证修复循环 → 自定义算子等最终关卡 → 迁移报告生成 → 经验评估与精炼

3. 自进化：越用越聪明

SEAM 有零先验运行、跨案例知识迁移、边际成本趋近于零等能力。 其中，每次迁移完成后，评估成功与失败的案例，把有效的适配方案提炼为可复用技能（skill）， 存入 .memory/skills/ 和 .memory/memory/ 目录，为下一次运行提供参考。

4. 幻觉控制：确保迁移结果真实有效

SEAM 采用行为验证、错误分类和精准路由、三振出局、 Fail-closed 门控、自定义算子验证证据链等策略，确保迁移结果真实有效。

「自进化」和「幻觉控制」是 SEAM 的核心能力，相辅相成，正向循环。

快速使用 SEAM 迁移 CUDA

快速完成您的第一次 SEAM 迁移

建议在「真正要运行迁移结果的国产 GPU 环境」中启动 SEAM。这样 SEAM 才能基于真实硬件反馈完成检测、运行、修复和验证。

步骤一：进入国产 GPU 环境，准备原始待迁移的项目仓库

在目标国产 GPU 服务器或容器中，例如阿里 PPU、昇腾 NPU 或沐曦 GPU。

准备一个原本可以在 NVIDIA CUDA 环境运行的 AI 项目仓库。该项目可以是 PyTorch、vLLM、SGLang 或其他待适配框架项目。

建议首次测试选择规模较小、入口清晰的项目，方便快速验证环境和迁移流程。

步骤二：启动 OpenCode Server

确认本机 OpenCode Server 已启动。默认地址为 http://127.0.0.1:4098。

如果端口不同，后续运行命令中需要通过 --server_url 指定。也可以由 SEAM 自动启动，前提是已经安装了 opencode 且需要用的 Token API Key 也已配好。

步骤三：运行 SEAM 的迁移指令

下载 SEAM，安装依赖，并在 SEAM 项目根目录运行：

bash 
# 下载和环境准备
git clone https://github.com/Fudan-SMI-lab/SEAM.git
cd SEAM
python3.10 -m venv .venv
source .venv/bin/activate

# 安装 SEAM 依赖
pip install -e "src/[dev,dashboard]"

# 运行 SEAM 迁移 CUDA 项目文件夹
bash src/scripts/run_seam.sh /path/to/your_original_cuda_project

如果您的 OpenCode 服务端口不同，可以运行：

bash — 指定 server 与输出目录 
bash src/scripts/run_seam.sh /path/to/your_original_cuda_project \
  --server_type opencode \
  --server_url http://127.0.0.1:4098

# 指定迁移后项目的输出位置
bash src/scripts/run_seam.sh /path/to/your_original_cuda_project \
  --output-dir /path/to/output_root

步骤四：等待 SEAM 自动处理

SEAM 命令行运行时，日志默认是简化输出的 TUI，也可以按 q 退出 TUI 直接以 log 输出运行。

根据 SEAM 的百模适配经验，绝大部分项目在 30 分钟内能完成迁移，最长的也有几个小时。 如果超过 30 分钟，建议查阅日志看迁移 phase 进度，以及看是否迁移异常。

步骤五：查看迁移结果和使用迁移后项目

  1. 迁移结束后，终端会显示是否通过端到端验证。常见成功标识包括：E2E TEST PASSED / E2E PASS。
  2. 迁移后的文件夹，在 --output-dir 用户指定目录，未指定则默认写入 SEAM 仓库同级目录：../output_projects/<项目名>_<时间戳>/。
  3. 根据 migration_reports/USAGE.md 文件中的 ## Run 章节建议运行指令来使用。

其他：看报告

  • 迁移报告位于迁移后的代码库下：output目录/migration_reports/
  • 详细运行时 log 位于：output目录/.sm-artifacts/
  • 更多运行 log，还可以根据迁移后的文件夹 migration_reports/USAGE.md 的指引，去 SEAM 目录的 SEAM/e2e-reports/src/<时间戳>/summary.json 获取。
如果运行失败，可以把 output-dir 文件夹中运行报告 migration_reports/ 和 .sm-artifacts/ 一起反馈给 SEAM 团队排查。 建议反馈时同时提供：原始项目名称或类型、目标 GPU 平台、执行的 SEAM 命令、终端失败信息、migration_reports/、.sm-artifacts/。

无论迁移成功与否，都可以贡献经验给 SEAM 服务端（功能开发中，待上线）。

常见问题

关于 SEAM 的高频疑问，逐条给出答案

SEAM 能做什么？什么是模型适配迁移？

SEAM 是一款基于 YAML 配置的轻量化模型适配迁移工具，核心作用是帮助开发者自动化、一键完成大模型跨硬件 GPU 迁移适配， 解决代码或模型从英伟达生态迁移至中国国产异构 GPU 算力硬件时，代码报错、算子不兼容、推理运行异常等适配难题。 SEAM 具备「自进化越用越聪明」「幻觉控制确保迁移结果真实有效」两大核心优势。

模型适配迁移，指将原本适配 CUDA 架构的大模型推理/训练代码、运行环境、调用逻辑， 适配至国产异构 GPU 硬件可运行、并且性能调优发挥好硬件本身能力。

SEAM 支持哪些 GPU 和框架？

  • GPUs：阿里平头哥 PPU、华为昇腾 Ascend、沐曦 MetaX 国产异构 GPU
  • 框架：PyTorch 原生框架、vLLM 高速推理框架、SGLang 大语言模型服务框架

如需交流或反馈，请通过 SEAM 开源仓库的 Issues 联系项目团队。

为什么要用 OpenCode？

SEAM 运行的时候，需要依赖 AI 模型 API 等服务。SEAM V1.0 版本使用的是 opencode （支持同时使用多个不同模型的开源 coding CLI，更适合在国产显卡的终端使用场景使用）， 未来我们也将适配到更多的 CLI 工具。 请用户在 opencode.ai 下载最新的版本，如一行指令 curl -fsSL https://opencode.ai/install | bash 安装。

阿里 PPU 和沐曦不是说兼容 CUDA，为什么也需要迁移？

硬件层面的 CUDA 兼容属于指令集/基础 API 浅层兼容，并非 100% 全量 CUDA 算子、底层内核、高阶接口完美兼容， 甚至每一版本的硬件发布实际都需要对应的调整兼容以发挥好硬件本身能力。 因此需要 SEAM 完成算子替换、底层调度逻辑改写、性能调优等，兼顾可用性 + 运行性能。

我没有中国产 GPU 环境，但想看看迁移效果来决定要不要买，能怎么实现？

两种解决方案：

  1. 当前各大中国国产 GPU 厂商都有提供测试渠道，可以联系对应厂商预约测试，建议提前准备好要运行的代码，并了解下我们 SEAM。

迁移的结果和报告我要怎么理解？

  1. 会直接在终端显示是否跑通：E2E TEST PASSED / E2E PASS 或失败信息；也可以通过 ./e2e-reports/migration_utils/<时间戳>/summary.json 获取更具体的信息。
  2. 迁移的代码库：会默认写入 ./output_projects/<项目名>_<时间戳>/，或是执行时输入的参数 --output-dir。您使用迁移后的代码库，即可在国产 GPU 上运行。
  3. 迁移报告：会在迁移后的代码库下创建 migration_reports/ 文件夹，用于查看迁移后项目本身的验收结果、性能、custom-op 迁移情况、构建日志等。
细节运行时 log 存在迁移后项目的 .sm-artifacts/ 下；如果运行失败，可以把运行报告和 .sm-artifacts/ 一起反馈给我们排查。 运行时 .memory 和 .skill 等文件夹会更新，是 SEAM 的自进化学习的经验记忆和技能素材，非必要勿删。

模型迁移流程

由工作流驱动的自动化流程：从环境检测开始，逐步完成项目分析、依赖准备、代码迁移、运行验证、错误修复和报告生成。

总体流程：
GPU 环境检测 → 用户项目分析 → 依赖准备 → 规则迁移 → 验证修复循环 → 自定义算子最终验证 → 迁移报告生成 → 经验评估与精炼

第一步：GPU 环境检测

SEAM 会检测当前运行环境，包括 Python 版本、PyTorch 版本、目标 GPU 是否可用、厂商软件栈是否存在等。

这一阶段的目标是确认当前环境是否具备迁移和运行条件。

第二步：用户项目分析

SEAM 会分析用户提供的原始项目，包括：

  • 项目目录结构
  • 依赖文件
  • 入口脚本
  • CUDA 调用模式
  • 是否包含自定义 CUDA/C++ 算子
  • 是否使用 PyTorch、vLLM、SGLang 等框架

这一阶段会决定后续走普通迁移路线，还是走更严格的 custom-op 迁移路线。

第三步：依赖准备

SEAM 会根据项目和目标平台准备运行环境，包括虚拟环境、Python 包、目标平台 PyTorch 版本、厂商 SDK 依赖等。

不同国产 GPU 平台的依赖安装方式可能不同，因此这一阶段需要结合平台策略执行。

第四步：规则迁移

SEAM 会先执行一轮确定性的代码迁移。这个阶段主要基于规则进行文本和接口替换，不依赖大语言模型自由生成。例如：

  • 替换设备调用方式
  • 调整导入语句
  • 修改通信后端
  • 处理目标平台相关配置

规则迁移可以快速处理大量明确、稳定的适配点。

第五步：验证修复循环

规则迁移完成后，SEAM 会运行迁移后的项目。若项目失败，SEAM 会进入验证修复循环：

  1. 执行入口脚本
  2. 捕获错误日志
  3. 分析错误类型
  4. 分派给对应修复角色
  5. 修改项目
  6. 再次运行验证

这个循环会持续到项目通过验证，或者达到最大迭代次数或停滞条件。

第六步：自定义算子最终验证

如果项目包含 CUDA/C++ 自定义算子，SEAM 会启用更严格的 custom-op 验证。

它不会只看脚本是否运行成功，还会检查：

  • 自定义算子是否被完整发现
  • 是否生成目标平台原生编译产物
  • 是否真的调用了自定义算子路径
  • 是否没有回退到 CPU 或内建算子
  • 精度是否通过对比验证
  • 性能报告是否完整
  • 构建日志是否包含目标平台证据

只有这些证据全部通过，才会标记为完整迁移通过。

第七步：迁移报告生成

SEAM 会生成迁移报告，用于帮助用户判断：

  • 项目是否端到端跑通
  • 迁移过程中修改了什么
  • 依赖和环境是否正常
  • 自定义算子是否完成适配
  • 性能表现如何
  • 失败时卡在哪个环节

第八步：经验沉淀

SEAM 会评估本次迁移的成功经验和失败教训，并将有效方案沉淀为可复用技能。后续遇到类似项目时，SEAM 可以参考已有经验，提高迁移效率和成功率。

这也是 SEAM 被称为 Self-Evolving 的原因。

迁移 CUDA 细节操作

运行 SEAM 前需要准备的基础环境与完整操作说明

SEAM 需要在目标国产 GPU 服务器或对应容器环境中运行。如果您希望把项目迁移到国产 GPU，就应当在对应硬件可访问的环境中启动 SEAM。

运行前准备

请先确认您已经准备好：

  • 原始 CUDA 项目代码
  • 一台可访问目标国产 GPU 的服务器或容器
    • Python 运行环境
    • 目标 GPU 平台对应的软件栈、驱动和 SDK
    • OpenCode Server 或 SEAM 当前支持的代码智能体运行服务

建议在「真正要运行迁移结果的国产 GPU 环境」中启动 SEAM。这样 SEAM 才能基于真实硬件反馈完成检测、运行、修复和验证。

如果您暂时没有国产 GPU 环境，可以先查看已完成迁移的案例报告，或联系对应 GPU 厂商预约测试环境；SEAM 网站的国产 GPU 页面也展示了当前免费可参与的国产 GPU 使用资源活动。

获取 SEAM 和运行环境依赖

获取 SEAM

在目标服务器或容器中下载 SEAM：

bash 
git clone https://github.com/Fudan-SMI-lab/SEAM.git
cd SEAM

安装 SEAM 依赖（如需）

bash 
cd SEAM
python3.10 -m venv .venv
source .venv/bin/activate

# 安装依赖
pip install -e "src/[dev,dashboard]"

启动或者校验 OpenCode Server

SEAM 运行时需要依赖 AI 模型 API 等服务。SEAM V1.0 版本使用的是 opencode，它支持同时使用多个不同模型的开源 coding cli，适合在国产显卡的终端使用场景中使用。

如需安装 OpenCode，可参考：curl -fsSL https://opencode.ai/install | bash

使用 SEAM 前，请先确认本机 OpenCode Server 已启动，默认地址为 http://127.0.0.1:4098，推荐在 SEAM 目录启动 OpenCode。比如启动指令如下：

bash 
opencode --help
opencode serve --hostname 127.0.0.1 --port 4098

# 确认 OpenCode server 在运行（可以不跑，只是用来检查的）
curl -s http://127.0.0.1:4098/global/health

也可以由 SEAM 自己启动 opencode。如果端口不同，SEAM 可以通过 --server_url 显式指定。

SEAM 基础运行命令

在 SEAM 根目录执行：

bash — 主要指令 
bash src/scripts/run_seam.sh /path/to/your_original_cuda_project

# 如果 OpenCode Server 端口不是默认值
bash src/scripts/run_seam.sh /path/to/your_original_cuda_project \
  --server_type opencode \
  --server_url http://127.0.0.1:4098

# 显式指定输出目录
bash src/scripts/run_seam.sh /path/to/your_original_cuda_project \
  --server_type opencode \
  --server_url http://127.0.0.1:4098 \
  --output-dir /path/to/output_root
位置参数
/path/to/your_original_cuda_project 是原始 CUDA 项目的路径
--server_type
表示使用 OpenCode Server
--server_url
表示 OpenCode Server 的服务地址
--output-dir
自定义输出文件夹目录地址，默认在 SEAM 目录的上层目录创建输出文件夹及具体任务子文件夹

默认工作流设置

不传 --workflow 时，启动器会使用 src/workflows/seam_auto_default.yaml 自动选择流程，通常无需手动指定 workflow。

项目根目录下的 ADAPTATION_REQUIREMENTS.md 会自动加载；非标准约束可以通过 --extra '--user-constraints PATH' 传入。

输出目录设置

运行完成后，迁移后的代码库默认写入 SEAM 仓库同级目录：../output_projects/<项目名>_<时间戳>。

也可以用环境变量 MIGRATION_OUTPUT_PROJECTS_ROOT 改默认根目录，或用 --output-dir 显式指定本次输出项目根目录。

SEAM 迁移结果、日志与报告

迁移中，SEAM 会自动执行类似如下动作：

  • 检测 GPU 和运行环境
  • 分析用户项目结构
  • 准备依赖环境
  • 执行代码迁移
  • 运行迁移后项目
  • 根据报错自动修复
  • 生成迁移报告
  • 沉淀可复用经验

SEAM 命令行运行时，日志默认是简化输出的 TUI，也可以按 q 退出 TUI 直接以 log 输出运行。

迁移是否成功

迁移完成后，请重点查看：是否跑通 —— 终端最后会直接显示 E2E PASS、E2E TEST PASSED 或失败信息。

迁移结果文件夹使用

SEAM 会展示迁移后结果 output-dir 的文件夹地址，该迁移后的文件夹会在原待迁移 CUDA 目录基础上增加文件：

  • migration_reports/ 文件夹，用于包含重要迁移结果，如 USAGE.md 中会展示迁移后的运行指令
  • .sm-artifacts/ 文件夹，详细运行时 log
如果运行失败，可以把 output-dir 文件夹中运行报告 migration_reports/ 和 .sm-artifacts/ 一起反馈给 SEAM 团队排查。 建议反馈时同时提供：原始项目名称或类型、目标 GPU 平台、执行的 SEAM 命令、终端失败信息、migration_reports/、.sm-artifacts/。

注意事项

SEAM 目录的 .memory、.skill 等文件夹会在运行中更新，是 SEAM 的自进化学习经验记忆和技能素材，非必要勿删。

普通代码迁移任务通常可以在较短时间内完成；具体耗时和 API 花费会受项目规模、错误修复轮数、模型 API 选择等因素影响。

E2E 测试契约（要点）

V3 E2E CLI、终态语义与产物契约 —— 面向需要做高级自动化与二次开发的用户。

本文描述当前可执行代码和确定性 fixture 已验证的 V3 行为。它不是 crash resume 设计，也不把 raw trace、replay 或工作目录 state 当作运行结果 authority。

生产支持契约：Linux 和 Python 3.10+。 Mandatory CI 只在无硬件 Linux runner 上验证支持下限和当前解释器，不声称验证真实 NPU/GPU。 Real accelerator checks remain optional and non-gating.

包依赖边界

  • base 安装包含 typing_extensions>=4.12,<5（core.compat 在 Python < 3.10 时回退使用，但生产 floor 已是 3.10+）。
  • [sqlite] 是可选 extra，提供 pysqlite3-binary>=0.5,<1 作为 stdlib sqlite3 的二进制回退；不安装 [sqlite] 只会禁用 session manager 的 SQLite completion evidence，不会让任何常规 runtime import 崩溃。
  • [dev] 提供 pytest / PyYAML / pydantic / tomli 测试工具链。
  • [dashboard] 提供 rich / textual 渲染器。
  • CI 永远只安装 base + [dev]，不把 [sqlite] 设为必需。

为什么不同 GPU 需要适配

即使某些国产 GPU 声称兼容 CUDA，也不代表所有 CUDA 项目都能直接运行。原因包括：

  • CUDA API 与目标平台接口存在差异
  • PyTorch 后端和设备管理方式不同
  • 厂商驱动、SDK、编译工具链不同
  • 自定义 CUDA 算子可能没有现成等价实现
  • 项目依赖版本与目标平台软件栈不匹配
  • 性能调优策略与硬件架构有关

因此，迁移不是简单的文本替换，而是需要结合真实硬件环境进行运行验证和修复。

平台策略差异

不同平台采用不同迁移策略。

对于原生转换型平台，例如部分 NPU 平台，SEAM 可能需要将 CUDA 相关调用转换为目标平台专用接口。

对于 CUDA 兼容型平台，例如 PPU，部分 torch.cuda 调用可能需要保留，因为目标平台通过兼容层支持相关接口。

SEAM 会根据目标平台策略选择对应迁移方式，并在运行过程中通过验证器检查迁移结果是否真实有效。

自定义适配经验报告的贡献原则

贡献适配经验时，重点是让别人能够判断、复现和复用。建议遵循以下原则：

  • 说明清楚原始项目、目标 GPU 平台和运行环境
  • 提供真实运行结果，不只描述代码修改
  • 保留关键命令、日志路径和报告路径
  • 明确哪些问题已经解决，哪些问题仍未解决
  • 删除密钥、内网地址、私有数据集路径等敏感信息
  • 只提交自己理解的内容；如果某个修复来自他人建议，需要说明来源或背景

什么是适配经验

适配经验是指某个项目从 CUDA 迁移到国产 GPU 过程中形成的可复用信息，包括：

  • 已完成迁移的模型案例
  • 不同 GPU 平台的适配经验
  • 依赖安装和环境配置说明
  • 某类错误的解决方法
  • 某个平台的依赖安装方式
  • 某个框架在目标 GPU 上的特殊配置
  • 自定义算子的迁移方法和经验
  • 性能验证和精度验证方式和报告
  • 可复现的测试脚本
  • 平台专用工作流和 prompt 模板
  • 避免 CPU fallback 的检查方法

适配经验应包含什么

建议一份适配经验至少包含：

内容说明
项目名称被迁移的模型或代码项目
原始环境原本运行的 CUDA、PyTorch、Python 等版本
目标平台阿里 PPU、昇腾 NPU、沐曦 GPU 或其他平台
使用框架PyTorch、vLLM、SGLang 等
问题现象报错信息或异常表现
解决方法实际采用的修改方式
验证结果是否端到端通过，是否有性能或精度报告
注意事项后续用户复用时需要注意的点

提交适配经验时，请尽量使用清晰、可复现的表达。

推荐写法：在昇腾 NPU 环境中，项目启动时报 xxx 错误。原因是依赖版本与 CANN 工具链不匹配。 将 xxx 版本调整为 xxx 后，入口脚本通过端到端验证，报告路径为 xxx。
不推荐写法：改了一些依赖后可以跑了。
