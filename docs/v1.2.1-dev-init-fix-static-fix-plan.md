## 2. 静态分析结论

### 2.1 报告存在两个目录模型，且缺少发布步骤

- Phase 6 把报告写入 `artifact_store.artifact_dir/reports`，即运行证据目录下的 `reports/`：`src/core/phase_runner.py:694`。
- `write_usage_guide()` 则在迁移项目下创建 `migration_reports/USAGE.md`，并无条件列出 `migration_reports/SUMMARY_REPORT.md`：`src/tests/e2e/e2e_test_v3.py:420-473`。
- 当前代码没有把 Phase 6 的 `SUMMARY_REPORT.md` 从证据目录发布到迁移项目的 `migration_reports/`。
- 因此，Bug 13、14、17 并非三个孤立问题，而是同一个“内部证据目录”和“用户交付目录”未建立显式映射的问题。

### 2.2 CLI 把报告目录叫作 Output，把迁移结果叫作 Temp

- `RunSummary.output_dir` 实际是 SEAM 本次运行报告目录；终端却打印为 `Output dir`。
- `RunSummary.temp_dir` 在用户指定项目时实际是保留的迁移后项目目录；终端却打印为 `Temp dir`。
- 对应代码位于 `src/tests/e2e/e2e_test_v3.py:367-417`。
- Shell 结束提示又使用日期通配符猜测目录，而不是使用 Python 已经确定的精确路径。

### 2.3 空目录校验发生得太晚，且只验证“目录存在”

- Shell 入口仅检查路径是否为目录：`src/scripts/run_e2e_v3.sh:377-388`。
- Python 主流程先分配报告目录、连接或启动 OpenCode，再复制项目：`src/tests/e2e/e2e_test_v3.py:746-864`。
- 没有“项目至少包含一个可迁移普通文件”的统一预检。
- 结果是空目录可以通过入口校验，并在启动 OpenCode 后进入工作流选择和 Phase 0。

### 2.4 OpenCode 存在两套启动逻辑，Shell 启动的进程无法被 Python 清理

- Shell 在服务不可达时用 `nohup opencode serve ... &` 启动服务。
- 随后 Python 看到端口已经可用，`resolve_server_url()` 返回 `(base_url, None)`，表示该服务不是本次 Python 进程拥有的子进程。
- Python 的 `ResourceCleanup` 只会停止非空的 `server_process`：`src/harness/run/cleanup.py:115-119`。
- Python 本身已有完整且安全的所有权实现：只有自己启动时才返回 `Popen`，已有服务返回 `None`；对应 `src/harness/server/lifecycle.py:332-410`。
- 所以应删除 Shell 的第二套启动职责，把自动启动统一交给 Python 生命周期管理。

### 2.5 日志时间混用了本地时间和 UTC

- 自定义 `log()` 使用 UTC，但格式没有 `Z`：`src/tests/e2e/e2e_test_v3.py:125-127`。
- `logging.basicConfig()` 使用 Python logging 默认的本地时间：`src/tests/e2e/e2e_test_v3.py:1616-1623`。
- `ui_events.jsonl` 和 telemetry 已使用带时区的 UTC ISO 8601。
- 因而同一事件在普通 logger 和工作流输出之间正好可能相差本地时区偏移，例如上海环境相差 8 小时。

### 2.6 复现说明使用了未经验证的 `.venv` 假设

- `write_usage_guide()` 固定写入 `source .venv/bin/activate  # if .venv exists`。
- 这无法表达 Phase 2 选择 base interpreter、已有 venv、项目 venv 或容器环境的不同情况。
- Phase 2 和 runtime report 已经保存环境、解释器及 namespace 信息，因此无需重新探测 GPU，也不应凭空假设 `.venv`。

## 3. 目标设计

建立四个清晰、互不混用的概念：

| 概念 | 建议字段/展示名 | 含义 |
| --- | --- | --- |
| 迁移项目目录 | `migrated_project_dir` / `Migrated project dir` | 用户最终使用的迁移后项目 |
| 用户报告目录 | `migration_reports_dir` / `Migration reports dir` | 迁移项目内、用户直接阅读的报告集合 |
| SEAM 运行证据目录 | `run_report_dir` / `SEAM run report dir` | `summary.json`、trace、telemetry、内部 artifacts 等运行证据 |
| 临时工作目录 | `temporary_work_dir` / `Temporary work dir` | 仅在确实是临时目录时使用，不能代指保留的迁移项目 |

原则：

1. 所有路径从真实 `Path` 对象或最终 summary 获取，不拼接日期通配符。
2. CLI 只打印已经确定的绝对路径。
3. `USAGE.md` 只能列出实际存在或明确标注“未生成”的文件。
4. 内部证据保留在 `.sm-artifacts`/run report 中；用户报告以受控方式发布到 `migration_reports/`。
5. OpenCode 只清理由本次 SEAM 进程启动的实例，不触碰用户预先启动的服务。

## 4. 分阶段实施方案

### 阶段 A：项目输入预检（解决 Bug 12）

新增一个无副作用的 Python 预检模块，例如：

```text
src/harness/project/preflight.py
```

建议接口：

```python
@dataclass(frozen=True)
class ProjectPreflightResult:
    project_dir: Path
    regular_file_count: int
    meaningful_file_count: int
    ignored_entries: tuple[str, ...]

def validate_project_input(project_dir: Path) -> ProjectPreflightResult:
    ...
```

校验规则：

- 路径必须存在、为目录且可读；
- 至少包含一个普通文件；
- `.DS_Store`、系统临时文件和空的版本控制元数据不计为可迁移内容；
- 不强制必须有 `.py` 文件，以免误伤 C/C++、模型配置或其他合法项目；
- 符号链接不跟随到项目目录之外做无限遍历；
- 失败错误应包含规范化绝对路径和“目录为空/仅含忽略项”的明确原因。

调用顺序必须调整为：

```text
解析参数
  → 项目输入预检
  → 分配 run report 目录
  → 连接/启动 OpenCode
  → 复制项目
  → 运行工作流
```

Shell 入口可调用同一 Python 预检模块，以保持 `--dry-run` 和直接 Python 调用的规则一致；Python 主入口仍必须再次校验，不能只依赖 Shell。

验收标准：

- 空目录返回非零退出码；
- 不创建输出项目副本；
- 不启动 OpenCode；
- 不创建会话、不进入 selector/Phase 0；
- 错误信息能区分“不存在”“不可读”“为空”。

### 阶段 B：报告发布与路径模型（解决 Bug 13、14、17）

新增确定性的报告发布器，例如：

```text
src/harness/run/report_publication.py
```

建议职责：

1. 从已验证的 `phase_6_report` canonical output 读取 `report_paths`；
2. 仅接受位于本次 artifact/report 根目录内的普通文件，拒绝路径穿越和任意外部路径；
3. 把报告原子复制到 `<migrated_project_dir>/migration_reports/`；
4. 生成一个 `report_manifest.json`，记录源路径、发布路径、大小和 SHA-256；
5. 检查必需文件，至少要求 `SUMMARY_REPORT.md`；
6. 发布完成后再生成 `USAGE.md`，其中只列出真实存在的报告；
7. 发布失败时不得打印 `E2E PASS`。应把它作为 required finalization stage，标记 finalization failure。

不建议直接让 LLM 把唯一报告写到用户目录。内部 canonical 报告仍应留在 artifact store，用户目录是经过验证的发布副本，便于审计和重试。

`write_usage_guide()` 应改为接收结构化的路径对象，而不是自行假设：

```python
write_usage_guide(
    project_dir=...,
    migration_reports_dir=...,
    run_report_dir=...,
    published_reports=...,
    reproduction=...,
)
```

终端输出建议固定为：

```text
E2E PASS
- Migrated project dir: /.../output_projects/foo_20260824_...
- Migration reports dir: /.../output_projects/foo_.../migration_reports
- SEAM run report dir: /.../SEAM/e2e-reports/src/e2e-v3-...
- Events log: /.../ui_events.jsonl   # 仅存在时显示
```

同步删除 Shell 末尾基于 `date` 的通配符提示，避免与实际 UUID run directory 冲突。

### 阶段 C：复现环境说明（解决 Bug 1）

新增一个纯数据的 reproduction contract，输入来自已保存的 Phase 2/3 与 runtime report，不做 GPU 探测：

```python
@dataclass(frozen=True)
class ReproductionContract:
    environment_kind: Literal["project_venv", "existing_venv", "base", "container", "unknown"]
    interpreter: str | None
    namespace: str | None
    container_id_or_image: str | None
    working_directory: str
    run_command: str | None
    setup_steps: tuple[str, ...]
    limitations: tuple[str, ...]
```

生成规则：

- `project_venv`：只有确认 venv 位于迁移项目内时才写 activation 命令；
- `existing_venv`：写实际解释器路径和复用说明，不复制用户环境；
- `base`：明确无需激活 venv，列出解释器和已验证命令；
- `container`：写容器 namespace、镜像/容器标识和容器内命令；
- `unknown`：不得声称可复现，明确指出缺失哪些证据。

输出放入 `migration_reports/USAGE.md`，也可同时生成机器可读的 `reproduction.json`。成功状态下如果既没有可运行命令，也没有明确限制说明，应视为报告发布失败。

### 阶段 D：OpenCode 生命周期收口（解决 Bug 15）

保留 Python `resolve_server_url()` 作为唯一启动入口：

- 服务已存在且可用：返回 `server_process=None`，运行结束不关闭；
- 服务不存在且允许自动启动：Python 启动并返回 `Popen`，最终由 `ResourceCleanup` 关闭；
- `--server-no-auto-start`：只检查，不启动；
- 本地端口被非可用进程占用：拒绝盲目重启或杀进程；
- 远端 URL：永不尝试本地启动。

Shell 中的 `nohup opencode serve ... &` 分支应删除。Shell 诊断只负责：

- 已就绪：继续；
- 未就绪且允许自动启动：提示“将由 SEAM 启动”，然后交给 Python；
- 未就绪且禁止自动启动：失败退出。

补充可观察输出：

```text
OpenCode server: auto-started by this run (pid=..., port=...); will stop during cleanup
```

或：

```text
OpenCode server: pre-existing at ...; left running
```

清理覆盖正常结束、工作流异常、KeyboardInterrupt、finalization failure。只依据保存的 `Popen`/ownership token 清理，禁止按端口扫描后杀进程。

### 阶段 E：统一日志时间（解决 Bug 16）

建议全链路采用 UTC ISO 8601：

```text
2026-08-16T17:29:31.872Z
```

实现方向：

- 新增统一时间函数和 UTC logging formatter，例如 `src/core/time_utils.py`；
- `log()` 使用同一 formatter，不再输出无时区的 `%Y-%m-%d %H:%M:%S`；
- Python `logging` 设置 formatter 的 converter 为 UTC；
- `ui_events.jsonl`、telemetry、summary 继续保留带时区 ISO 格式；
- 不修改第三方工具原始日志内容，但在汇总或转录时保留来源并明确时区未知。

兼容策略：本轮只改变人类可读日志格式，不改变已经使用 ISO 8601 的 JSON schema 字段名。

### 阶段 F：文档和兼容性收尾

同步修改：

- `docs/User_Guide.md`：明确三类目录和报告发布规则；
- `docs/FAQ.md`：移除过时的 `.migration_reports/` 表述；
- `src/docs/E2E_TESTING.md`：记录空目录预检和 OpenCode ownership；
- `src/scripts/run_seam.sh --help`、`run_e2e_v3.sh --help`：说明自动启动服务会在本次运行结束后关闭，预先存在的服务不会被关闭。

## 5. 推荐提交拆分

建议拆成五个可独立回滚的提交：

1. `fix(preflight): reject empty migration projects before side effects`
2. `fix(reports): publish canonical reports into migrated project`
3. `fix(usage): render evidence-based reproduction instructions`
4. `fix(server): centralize opencode ownership and cleanup`
5. `fix(logging): standardize timestamps and path labels`

依赖顺序为 1 → 2 → 3；第 4、5 项可并行开发，但最终应在统一的 CLI 契约测试中合并验证。

## 6. 无 GPU 测试方案

本轮所有验收均可在 CPU/本地临时目录中完成。

### 单元测试

| 测试区域 | 用例 |
| --- | --- |
| 项目预检 | 不存在、文件路径、空目录、仅 `.DS_Store`、含一个普通文件、不可读目录、外部符号链接 |
| 报告发布 | 完整报告、缺少 summary、源路径越界、目标已有旧文件、复制中断、哈希一致性 |
| 使用说明 | project venv、existing venv、base interpreter、container、unknown 五种 contract |
| 路径输出 | 确保输出真实绝对路径，禁止 `*_YYYYMMDD_*` 猜测和 `Temp dir` 误称 |
| 时间 | 固定时钟下 `log()`、logging、UI event 输出同一 UTC 时刻并含 `Z` |
| 服务生命周期 | 预先存在服务不关闭；本次启动服务会关闭；异常和中断也关闭；远程服务不启动 |

### 静态集成测试

使用 `tmp_path`、假的 SessionManager、假的 `Popen` 和最小 Phase 2/3/6 artifact：

1. 构造一个只有 `main.py` 的项目；
2. 注入假的 Phase 6 报告文件；
3. 执行 finalization/report publication；
4. 验证 `migration_reports/SUMMARY_REPORT.md`、`USAGE.md`、manifest 均存在；
5. 验证 USAGE 中命令来自 Phase 3，环境说明来自 Phase 2；
6. 验证 summary 的三个目录语义准确；
7. 全程不访问 GPU、网络或真实 OpenCode。

### 建议测试命令

```bash
python -m pytest \
  src/tests/test_project_preflight.py \
  src/tests/test_report_publication.py \
  src/tests/test_usage_guide_docs.py \
  src/tests/test_server_lifecycle.py \
  src/tests/run_cleanup_oracle_cases.py \

```

实现完成后再运行与 V3 runner/finalizer 相关的完整 CPU 测试集。PPU、沐曦和其他 GPU E2E 测试明确标记为 deferred，不用假 PASS 替代。

## 7. 完成定义

本轮静态修复完成需同时满足：

- 空目录在任何 OpenCode/LLM 副作用前失败；
- `USAGE.md` 中列出的报告全部真实存在；
- CLI 能明确区分迁移项目、用户报告和 SEAM 运行证据目录；
- 复现说明不再无条件假设 `.venv`，而是忠实反映 Phase 2/3 环境；
- SEAM 自动启动的 OpenCode 在所有退出路径被清理，预先存在的服务保持运行；
- 同一事件的 SEAM 自有日志时间一致并显式标注 UTC；
- 上述行为由不依赖 GPU、网络和真实 OpenCode 的自动化测试覆盖；
- PPU 与沐曦三个问题保持开放，文档明确标记为后续 GPU 环境验证项。
