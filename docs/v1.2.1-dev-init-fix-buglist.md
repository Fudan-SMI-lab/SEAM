## Bug 细节

### 1. [P0 / ReOpen] 迁移成功日志中的路径非法（表中序号 13）

- 关联版本：`v1.2.1-dev-init-fix` 的 `07d77fc`。
- 现象：问题在修改后仍可复现；迁移成功界面或日志中标出的路径实际不存在。
- 原始记录同时关联了 2026-08-12 的 V1.2 演示视频作为参考。
- 风险：用户依据成功日志寻找产物时会进入不存在的目录，无法定位报告或迁移结果。
- 修复要求：成功日志中的路径必须来自最终真实产物路径，不能由旧目录约定或展示字符串拼接得出。
- 建议验收：对一次成功迁移逐一检查日志中展示的报告、事件日志和输出目录，所有路径都应存在且可读。

### 2. [P0 / New] 日志向用户展示的 Report 地址错误（表中序号 14）

- 关联版本：`v1.2.1-dev-init-fix` 的 `07d77fc`。
- 复现场景：以空目录作为输入运行迁移。
- 原始日志：

  ```text
  Dashboard closed (q). Migration continues in background.
  Report dir: /public/wuyou_2_keshan/SEAM/e2e-reports/src/e2e-v3-d18f23b999bd
  Events log: /public/wuyou_2_keshan/SEAM/e2e-reports/src/e2e-v3-d18f23b999bd/ui_events.jsonl

  E2E PASS
  - Output dir: /public/wuyou_2_keshan/SEAM/e2e-reports/src/e2e-v3-d18f23b999bd
  - Temp dir: /public/wuyou_2_keshan/output_projects/emptyfolder_20260816_165324 (kept)
  ```

- 现象：记录明确指出 Report 地址错误；同时 `Report dir`、`Output dir`、`Temp dir` 的命名概念混乱。`Report dir` 与 `Output dir` 指向同一路径，而 `Temp dir` 看起来更像最终通过后的迁移输出。
- 修复要求：明确并统一三个目录的语义与展示名称，日志必须打印真实路径。
- 建议验收：成功和失败流程分别验证 `Report dir`、`Events log`、迁移结果目录、临时目录；存在性、内容和名称语义应一致。

### 3. [P1 / New] 空输入目录仍长时间执行（表中序号 12）

- 复现命令：

  ```bash
  bash src/scripts/run_seam.sh ../models/emptyfolder/
  ```

- 输入条件：目标目录存在但内容为空，`ls -l` 显示 `total 0`。
- 现象：程序没有在入口处识别无可迁移内容，仍启动 OpenCode 和完整工作流。早期复现中运行约 20 分钟后仍停留在 `phase_0_env_detect (llm)`。
- TUI 表现：环境检测显示“运行中”，后续阶段一直“待执行”，没有明确提示输入目录为空。
- 附带观察：记录中还包含一次错误的绝对路径输入，程序能报告 `Project directory not found` 并列出搜索路径；该行为与“存在但为空”的情况应区分处理。
- 修复要求：在启动 OpenCode、创建会话或进入 LLM 阶段前校验项目目录是否含有可分析内容；为空时快速失败并给出可操作提示。
- 建议验收：分别覆盖不存在目录、空目录、仅含隐藏元数据的目录、正常项目目录，确认空目录不会启动耗时迁移流程。

### 4. [P1 / New] 迁移说明引用了错误的汇总报告路径（表中序号 17）

- 建议验收：迁移完成后，从 `USAGE.md` 中给出的路径可以直接打开 `SUMMARY_REPORT.md`。

### 6. [P2 / New] 沐曦平台 DeepSeek 模型适配失败（表中序号 4）

- 模型：[DeepSeek-R1-Distill-Qwen-1.5B-Q4_0-GGUF](https://www.modelscope.cn/models/ggml-org/DeepSeek-R1-Distill-Qwen-1.5B-Q4_0-GGUF/summary)。
- 复现命令：

  ```bash
  bash src/scripts/run_seam.sh \
    /workspace/project/DeepSeek-R1-Distill-Qwen-1.5B-Q4_0-GGUF \
    --server_type opencode
  ```

- 根因描述：`llama.cpp` CUDA 后端依赖 MACA cu-bridge 不支持的 NVIDIA PTX 内联函数，包括 `__dp4a`、`ldmatrix`、`cp.async`，导致 GPU 编译被阻断。
- 当前降级结果：采用 CPU `llama-cpp-python` 绑定可稳定推理；128 token 约 13.8 秒（9.3 tok/s）。环境中的 MetaX Torch `2.8.0+metax3.5.3.9` 可识别 8 张 C550，但该项目不是 PyTorch 架构，未能利用 GPU。
- 修复要求：给出沐曦平台可用的 GPU 构建/后端方案，或明确识别不兼容并执行可解释的 CPU 降级，不能让编译失败成为无结论终点。
- 建议验收：在目标沐曦环境完成构建与推理，并在报告中明确实际使用的后端、设备和性能。

### 7. [P2 / New] PPU + vLLM 配置失败（表中序号 7）

- 现象一：fixer 在临时容器内执行 `pip install`，但验证阶段重新创建容器后修复丢失，依赖修复不持久。
- 现象二：smoke test 已返回 `exit 0`，但 `custom_op_final_gate` 未触发，工作流没有按成功条件退出。
- 原始记录附件：`mineru_vllm_failure_analysis.md`。
- 修复要求：依赖修复应写入后续验证使用的环境/镜像；成功退出条件应覆盖 smoke test 已通过的路径。
- 建议验收：修复后重新创建验证容器仍保留依赖，且 smoke test 成功会触发 final gate 并正常结束工作流。

### 8. [P2 / New] PPU + SGLang 配置失败（表中序号 8）

- 现象一：`error_analyzer` 清空 todo 后没有提供 dispatch route，导致派发死锁。
- 现象二：PPU 私有包索引缺少构建依赖 `setuptools>=77.0.3`。
- 原始记录附件：`mineru_sglang_failure_analysis.md`。
- 修复要求：todo 被清空或分析完成后必须产生明确的下一跳/终止状态；依赖解析需支持 PPU 私有源缺包时的可用策略和清晰错误提示。
- 建议验收：模拟缺少构建依赖和 todo 被清空两种情形，工作流均不得无期限等待。

### 9. [P2 / New] 日志时区不一致（表中序号 16）

- 关联版本：`v1.2.1-dev-init-fix` 的 `07d77fc`。
- 同一时刻出现两套时间：

  ```text
  2026-08-17 01:29:31,872 core.workflow_selector INFO ...
  [2026-08-16 17:29:31] Workflow selector result ...
  ```

- 两者相差 8 小时，表现为本地时间与 UTC 混用。
- 影响：用户难以按时间关联 TUI、Python logger、事件日志和智能体工作流日志。
- 修复要求：统一日志时区和格式；建议显式带时区偏移（例如 `+08:00` 或 `Z`），避免无时区时间戳。
- 建议验收：`core.*`、`Workflow`、TUI、`ui_events.jsonl` 对同一事件输出一致且可解析的时间。

### 10. [P3 / New] OpenCode 服务退出策略不明确（表中序号 15）

- 关联版本：`v1.2.1-dev-init-fix` 的 `07d77fc`。
- 场景：运行前 4098 端口无服务，SEAM 自动执行 `opencode serve --hostname 127.0.0.1 --port 4098`。
- 诉求：需要明确 SEAM 运行结束后，自动启动的 OpenCode 是保留以便下次复用，还是由 SEAM 负责关闭。用户看到多个 OpenCode 进程时不敢手动关闭，无法判断是否仍有任务使用。
- 原始详情存在证据不一致：文字称 E2E 通过后 4098 服务仍在，但附带的后续 `ps` 只显示 `grep opencode`，健康检查也无返回。实现和测试时应先确认稳定复现结果。
- 修复要求：区分“SEAM 本次自动启动”和“用户预先启动”的服务；只清理本次拥有的进程，或明确输出保留状态、PID、端口和安全关闭方式。
- 建议验收：覆盖预先已有服务、SEAM 自动启动服务、正常结束、异常退出和中断五种路径，确保不误杀外部服务且不遗留无主进程。
